# Architecture & Decision Records

## System overview

```
                       ┌────────────────────────────────────────┐
  Web UI (no build) ──▶│              src/server.js             │
  VS Code extension ──▶│   REST API + SSE + static + auth       │
  Browser extension ──▶│                                        │
  ChatGPT Actions ────▶│  ┌──────────┐  ┌─────────┐  ┌───────┐  │
                       │  │ chat.js  │─▶│providers│─▶│ Ollama│  │
  MCP clients ────────▶│  │orchestr. │  │ gateway │  │FreeTok│  │
  (Claude, Codex,      │  └────┬─────┘  └─────────┘  │ OpenAI│  │
   Cursor, Gemini) ───▶│       │                     │ compat│  │
        src/mcp.js     │  ┌────▼─────┐  ┌─────────┐  │Anthro.│  │
                       │  │  db.js   │  │  rag/   │  └───────┘  │
                       │  │ SQLite   │  │ chunker │             │
                       │  │ (local)  │  │ BM25    │             │
                       │  └──────────┘  │ hybrid  │             │
                       │                └─────────┘             │
                       └────────────────────────────────────────┘
```

One chat turn (`POST /api/chat`): resolve persona → load trimmed history → inject long-term memory notes (if persona uses memory) → retrieve top-k knowledge chunks for the query (if persona uses knowledge) → compose system prompt → stream from the provider → persist both turns + usage → emit SSE (`meta`, `reasoning`*, `delta`*, `done`). `reasoning` frames (a model's chain-of-thought, when the server exposes it) are shown live in the browser and never persisted (ADR-25). `meta` carries `outgoing: { bytes, chars, approxTokens, host } | null` — the receipt of what left for a remote provider, `null` when the provider is local — and `POST /api/chat/preview` returns the same assembled context before anything is sent (ADR-26).

One Model Studio build (`POST /api/model-recipes/:id/build`): load the user-owned recipe from SQLite → validate its base model, system prompt, parameters, template, license, quantization, and seed messages → render a portable Modelfile → call `/api/create` at the configured Ollama endpoint → return both build status and ownership metadata. Recipe persistence and model-artifact storage are intentionally separate boundaries.

One fine-tuning run: explicitly select conversations → derive one-turn supervised examples → review/redact and save every included pair → freeze a deterministic conversation-grouped train/eval snapshot → bind consent to its hash and canonical trainer endpoint → content-address and upload both JSONL blobs → submit one idempotent LoRA/QLoRA job → poll the trainer's authoritative state → inspect evaluation-specific holdout metrics → record approval/rejection/skip notes → verify the trainer-attested Ollama tag and digest → assign it to a persona. `src/training/` owns the pure dataset and wire-contract logic; the external user-operated trainer owns Python/accelerator dependencies and weight updates.

## Decision records

### ADR-1: Zero runtime dependencies
The product promise is sovereignty; a 400-package `node_modules` is a supply chain the user can't audit. Node 22 provides everything needed natively: `node:sqlite`, `node:http`, `fetch`, `node:crypto`, `node:test`. Consequence: we hand-roll small things (router, SSE parser, BM25) — each is <150 lines and testable. Dev-time tools (e.g. `vsce` for packaging the VS Code extension) are acceptable; runtime deps are not.

### ADR-2: SQLite via `node:sqlite`
Single-file, user-ownable, trivially exportable, no server. The module is experimental in Node 22 but API-stable enough; we suppress the warning with `--no-warnings`. Fallback plan if it regresses: the `Store` class is the only touchpoint — swappable for a JSON-file store without touching callers.

### ADR-3: Provider gateway as async generators
Every provider implements `chatStream()` yielding `{type:'reasoning'|'delta'|'done'}` — `reasoning` is optional and carries chain-of-thought when the wire exposes it (OpenAI-compat `reasoning_content`/`reasoning`, Ollama `thinking`, Anthropic `thinking_delta`); consumers that only want the answer ignore it, and only `delta` text is ever persisted (ADR-25). SSE (Anthropic/OpenAI-compat) and NDJSON (Ollama) parsing are isolated in `providers/parsers.js`. Anthropic is spoken natively (Messages API, `anthropic-version: 2023-06-01`) — never through an OpenAI-compat shim; note that modern Claude models reject `temperature`, so the gateway never sends sampling params to Anthropic.

### ADR-4: Hybrid retrieval with graceful degradation
Embeddings (Ollama `/api/embed`) are optional. Every chunk is always BM25-indexable; when embeddings exist for both query and chunks, scores blend (0.65 semantic + 0.35 keyword). Consequence: knowledge search works on a fresh machine with no models pulled, and silently upgrades when an embedding model appears.

### ADR-5: MCP as the universal AI-platform integration
Rather than one bespoke plugin per AI product, `sovereign mcp` (stdio JSON-RPC) surfaces memory/knowledge/chat as MCP tools. Claude Desktop/Code, Codex CLI, Cursor, Windsurf, and Gemini CLI all consume it with a few lines of config. ChatGPT is the exception (Actions + OpenAPI + tunnel) — handled separately.

### ADR-6: Localhost-first, tunnel-safe security
Server binds `127.0.0.1`. When `authToken` is configured, every API request—including loopback traffic from a local tunnel or reverse proxy—requires Bearer auth. Tokenless localhost mode permits native clients but rejects unsafe browser origins, untrusted Host headers, and non-JSON mutations. Browser bootstrap tokens travel in the URL fragment (never the HTTP request) and are then stored locally. API keys are masked in browser config responses; portable exports omit configuration entirely, and masked values sent back by the UI preserve the real secret.

### ADR-7: No-build web UI
Vanilla HTML/CSS/JS served statically. No bundler, no framework, no telemetry. Chat streaming reads the SSE body via `fetch` + `ReadableStream` (POST-based SSE, since `EventSource` is GET-only). Markdown rendering is a minimal escaped-first subset (code fences, inline code, bold, links).

### ADR-8: Zero-dep document ingestion
DOCX is a ZIP of XML; PDF text lives in content streams. Both are parseable with Node built-ins: a ~70-line ZIP reader (`ingest/zip.js`, stored + deflate via `zlib.inflateRawSync`) feeds the DOCX extractor, and the PDF extractor inflates FlateDecode streams and walks the text operators (Tj/TJ/'/"/Td/T*). Best-effort by design: unreadable output (scanned pages, CID fonts) fails loudly with a clear message instead of indexing noise. Binary uploads travel as base64 JSON (`contentBase64`) to keep the API surface JSON-only.

### ADR-9: Auto memory extraction is opt-in and fire-and-forget
When `memory.autoExtract` is on, each chat exchange triggers one background model call that distills ≤3 durable facts into memory notes. It never blocks or delays the chat stream, failures are silent, and parsing tolerates model quirks (bullet variants, stray NONE lines). Off by default: it costs a model call per exchange and users should choose to be profiled, even locally.

### ADR-10: Model Studio creates configurable Ollama artifacts, not trained weights
Model Studio stores editable model recipes and builds them through the configured Ollama endpoint's `/api/create`. A recipe can describe the artifact name, base model, system prompt, inference parameters, prompt template, license, quantization, and seed messages. The build returns a readable Modelfile and produces a named model artifact that can be used outside SovereignAI on that Ollama endpoint. Quantization is passed only for eligible FP16/FP32 sources; an unsupported source/format combination remains an Ollama build error rather than being silently changed.

This is model packaging, inference configuration, and optional quantization—not weight fine-tuning. Building does not train on conversations, update the source model, or create a new foundation model. When quantization is selected, Ollama transforms the derived artifact's weight representation to the requested lower precision. That distinction is part of the product contract: the UI and API may say "build" or "create artifact," but must not imply that a recipe performs training. Fine-Tuning Studio is a separate workflow with its own consent and trainer boundary.

### ADR-11: Ownership is explicit at every storage and processing boundary
SovereignAI owns no hosted control plane. Workspace records and model recipes live in the user's selected home as SQLite state; the code is inspectable and fair-source licensed (FSL-1.1-MIT, converting to MIT per release after two years); full-workspace JSON export/import carries every portable data table, including `model_recipes`. Runtime configuration and secrets are intentionally excluded from that export so a backup can be moved without silently copying credentials or redirecting restored data to an old endpoint.

A model artifact lives at the Ollama endpoint that built it. With a loopback endpoint, recipe inputs and artifact storage stay on that machine. With a non-local endpoint, build inputs cross the network and the artifact is stored by that remote Ollama service. The API reports this boundary rather than labeling every Ollama build "local." SovereignAI does not mirror or escrow the resulting weights, so artifact backup and deletion follow the operator's Ollama procedures. Portable export carries the recipe and Modelfile ingredients, not Ollama weight blobs. User control of a recipe and generated artifact does not supersede third-party base-model licenses; the recipe's `license` field is metadata, not a license grant from SovereignAI.

### ADR-12: Fine-tuning is an external, endpoint-bound weight-training protocol
SovereignAI remains a dependency-free control plane. It can curate and validate training data but cannot honestly hide Axolotl, TRL/PEFT, Unsloth, MLX-LM, drivers, and accelerator requirements inside the Node process. Training therefore uses a small, versioned HTTP contract to a trainer the user operates. The capability handshake must assert actual weight training; blobs are immutable and content-addressed; job creation uses a stable idempotency key; indeterminate jobs block duplicates and retry the same key; imported snapshots are revalidated before upload.

Source consent records the exact canonical trainer endpoint disclosed during curation. Final run consent records dataset hash, current endpoint, base model, method, and normalized hyperparameters; a changed endpoint therefore requires a fresh run confirmation while retaining the original snapshot audit trail. Credentials/private keys are blocked rather than merely acknowledged; other personal-data and quality flags require explicit acceptance. The trainer may register a merged GGUF in Ollama, but one-click assignment additionally compares the trainer-attested Ollama digest with the configured Ollama tag. Adapter/checkpoint and model deletion remain responsibilities of the trainer and Ollama operators. There is no OpenAI fine-tuning adapter or hosted fallback.

### ADR-13: Single binaries embed the untouched module graph, not a bundle
Node SEA requires a CommonJS main script, but bundling would ship rewritten code the user can no longer diff against this repository. Instead, `scripts/sea/boot.cjs` registers synchronous module hooks (`module.registerHooks`, Node 22.15+) that serve the byte-identical ES-module graph and web UI from assets embedded in the executable under a virtual URL scheme; `scripts/sea/manifest.mjs` walks the import graph and fails the build on any bare or unresolvable specifier. `postject` — the injector Node's own SEA docs prescribe — runs via npx at build time only; the runtime stays zero-dependency. The binary behaves like an installed launcher: it defaults to the stable home (`%LOCALAPPDATA%\SovereignAI` / `~/.sovereignai`) unless `SOVEREIGN_HOME` overrides it. Consequence: binaries are unsigned (ad-hoc signed on macOS), so first launch may need a SmartScreen/Gatekeeper confirmation; that trade-off is documented rather than hidden behind a signing service.

### ADR-14: Hugging Face browse is a read-only metadata lookup, never a weight proxy
Model Studio's base model field already accepted any string, including a `hf.co/<owner>/<repo>[:<quant>]` reference — Ollama's `/api/create` resolves that itself. `src/hf-catalog.js` adds a search-and-browse UI on top of that existing capability; it does not add a new class of thing SovereignAI can build. The server calls a single fixed host (`huggingface.co`), never a user-supplied one, so this intentionally does not route through the provider-URL SSRF allow/deny logic in `config.js` (ADR-6's guard exists for user-configured endpoints; there is no user-configured endpoint here to abuse). `safeFetch`'s no-redirect rule still applies. No model weights transit this server in either direction: a build still pulls straight from Hugging Face to the configured Ollama endpoint, exactly as a hand-typed `hf.co/...` base always has.

### ADR-15: GPU marketplace provisioning splits on compute style, not on provider
`sovereign byoc gpu` (rail 1.5, `src/byoc/providers/` + `gpu-provision.js`) rents a box instead of requiring the operator to already own one, but RunPod/Vast.ai and Lambda Cloud are not the same shape of thing: the first two rent a Docker *container* with no daemon inside to nest `docker build`/`docker run` in, while Lambda rents a real VM. Rather than force every provider through rail #1's SSH pipeline (which would silently not work for two of three), the code branches on a declared `computeStyle`: `'container'` providers run a pinned, pullable image directly and are reached over their mapped HTTP port — no SSH at all — while `'vm'` providers get a dedicated per-provider SSH keypair and hand off to `connector.js` `deploy()` completely unchanged once reachable. This means `computeStyle: 'container'` instances necessarily break rail #1's strongest security property: `SOVEREIGN_TOKEN` is generated by the CLI process and sent as instance env, because there is no host we control to generate it there instead. That deviation is disclosed in the deploy plan printed before every provisioning action, not hidden. Unlike every other feature added this session, none of the three provider clients could be verified against live infrastructure (no test accounts) — each file's header names the exact fields most likely to have drifted from the provider's current API.

### ADR-16: Chat-history import is tiered by verifiable confidence, with a generic format as the universal fallback
`src/chat-import/` (`chatgpt.js`, `claude.js`, `gemini.js`, `generic.js`) lets an operator bring conversation history in from another AI platform. Rather than build a same-effort dedicated parser for every named platform (ChatGPT, Claude, Gemini, Grok, Kimi, GLM, DeepSeek, Qwen), each gets only as much bespoke code as its export format could actually be verified against: ChatGPT and Claude both have official, publicly well-documented, stable export schemas, so those parsers are built with real confidence. Gemini's only known export path (Google Takeout's "My Activity" JSON) is an activity log, not a conversation export, and was not verified against a live account — its parser is explicitly marked experimental and imports prompts only, never guessing at a response field that may not exist. The remaining platforms have no self-serve bulk export this could verify, so rather than guess at unknowable schemas, they're all pointed at `generic.js` — a documented, flexible JSON shape that is the answer for any current or future platform without dedicated support, not a lesser fallback bolted on afterward. Every parser is a pure function (`detect`/`parse`) with no store or filesystem access, callable from `src/chat-import/index.js`'s dispatcher, which reuses the existing zero-dep ZIP reader (`src/ingest/zip.js`) to open the ZIP both ChatGPT's and Claude's exports arrive in. Imported conversations carry `source_platform`/`external_id` (new nullable, uniquely-indexed columns) so re-running the same import is idempotent rather than duplicating history, and those two fields round-trip through the native `sovereign export`/`import` backup format like every other column.

### ADR-17: Memory provenance is recorded, never fabricated
The memories table gains `origin` ('manual' | 'extracted' | 'distilled'), `source_conversation_id`, and `updated_at`. Every write path states how a memory entered the system; edits stamp `updated_at`. Two honesty rules shape the design. First, rows that predate tracking keep `origin = NULL` and are shown as "recorded before provenance tracking" — backfilling 'manual' would be fabricated provenance. Second, `source_conversation_id` is provenance metadata, not a foreign key: deleting the conversation later doesn't falsify where the memory came from, so the pointer survives as a historical record ("from a since-deleted conversation").

Deliberately deferred: supersession chains / an append-only edit ledger. Making "amend" keep the previous content as a superseded row silently retains data the user may have edited *specifically to remove* — in a sovereignty product, invisible retention is worse than absent lineage. An edit ledger ships only together with UI that makes retention visible and strikable (the Memory Ledger surface is the natural home). Until then, edits are in-place and deletion is deletion.

### ADR-18: Portability is verifiable and bidirectional
Four decisions, one theme — the exit path is a product surface, and it must work in both directions:

1. **Verified archives.** Exports carry a manifest: SHA-256 per table over the canonical JSON serialization, plus one archive digest ([format spec](EXPORT_FORMAT.md)). Import refuses a mismatching archive and names the differing tables; the documented escape hatch for deliberate hand-edits is deleting the `manifest` key. The manifest is integrity, not authenticity — there is no signing key, and the docs say so instead of implying more.
2. **Encrypted archives** (`export --encrypt`): AES-256-GCM, scrypt-derived key, all parameters except the passphrase recorded in the self-describing envelope. This protects archives at rest (rented GPU hosts, shared drives, cloud backups). It deliberately does not encrypt the live database and does not change what a BYOC host operator can read at runtime — rail 1.5's disclosed exposure stays disclosed.
3. **The portfolio** (`sovereign portfolio`, `GET /api/portfolio`): a markdown seed crystal — memories with provenance, personas with system prompts, knowledge inventory — built for pasting into *other* tools. Import doors into AI platforms are one-way by design; this is the outbound door. It is distillation, not backup: conversations and document contents stay out.
4. **Distillation** (`sovereign distill`, `import-chat --distill`): imported history is archive prose until a model sweeps it for durable facts — exactly the "flattening" we criticize elsewhere, so the sweep exists. Opt-in (one model call per conversation, costs are printed), sequential, idempotent via `conversations.distilled_at` (set even when a sweep finds nothing), and CLI-first: the server has no job queue, and hundreds of background model calls with no progress surface would be opaque. Distilled memories carry `origin: 'distilled'` and their source conversation.

### ADR-19: The first five minutes — Arrival, the Mind view, and streamed distillation
A chat box is a commodity surface, and every differentiator this product has lives in the data plane — so the app's front door is now the data plane. Three additive pieces (nothing prior was removed; the command center, wizard, and all views remain):

1. **The Mind view** (`/api/mind`, default landing) — a control room for the context layer: memory counts by provenance origin, the latest entries with their receipts, imported-history state, and outbound doors (portfolio, MCP, editors, verified export). It shows only what the server actually knows: there is deliberately no "connected" status for MCP clients or extensions, because those connect through their own processes and claiming live status would be theater. Pre-provenance memories are labeled "recorded before provenance tracking," not guessed.
2. **Arrival** — a post-setup overlay (auto-opens once on an empty workspace; permanently reachable from the Mind view) that runs the import → distill → reveal arc: drop a ChatGPT/Claude export, watch memories ignite as they are distilled with provenance attached, then get a model-generated greeting grounded in what was just learned. It runs *after* setup, not inside the wizard, because distillation needs a configured provider and the wizard only persists provider config at its final step. The greeting is a bonus on top of real stats — if the model call fails, the reveal stands on the numbers; if nothing durable was found, it says so instead of padding.
3. **`POST /api/distill` (SSE)** — the streamed counterpart to `sovereign distill`, same contract (sequential, one call per conversation, `distilled_at` idempotency, first error stops the run and the failed conversation stays sweepable). The CLI remains the right tool for very large archives; the API bounds each run (default 40, max 500 conversations per request).

### ADR-20: Cognition sovereignty — authored memory, local-only extraction, audited claims
The v0.5 provenance work exposed a gap it had itself created: once models write long-term memory (auto-extract, distillation), the *lens deciding what is durable about you* may belong to a remote provider — sovereign storage, borrowed cognition. Three responses:

1. **Machine-written memories name their author.** `memories.author_provider` / `author_model` record which model wrote every extracted/distilled row (NULL = human-authored or pre-tracking). The Memory view, Mind ledger, and export format all carry it. Closing our own provenance hole beats explaining it.
2. **"Cognition stays home"** (`memory.extractLocalOnly`): memory-writing model calls are refused unless the provider endpoint is local (loopback or Docker-internal, matching the UI's "Local" badge; Anthropic is remote by definition). Chat may still go remote — the user's choice — but with the switch on, what gets *learned about them* is decided only by models on their hardware. Auto-extract skips silently (its fire-and-forget contract); distillation fails loudly (it is a deliberate foreground act).
3. **Claims are audited, not asserted.** [docs/SOVEREIGNTY.md](SOVEREIGNTY.md) is a public per-layer ledger — sovereign / conditional / borrowed, each with its compromise and its exit — maintained under the same rule as the product: unknowns are reported as unknown. Releases now ship `SHA256SUMS.txt` (minisign-signed once the maintainer adds a key), and clone-and-run-from-source is documented as the zero-trust path. [docs/WHY.md](WHY.md) states the thesis the ledger defends: the fragmented-self reassembled under user control.

### ADR-21: Life Import rail #1 — email, heuristics-first, evidence attached, never an archive
The fragmentation thesis (docs/WHY.md) needs an acquisition strategy that doesn't die where every aggregator died: credential custody. Rail #1 therefore eats the export a normal person can actually get — the Takeout/standard mbox — with the same tiered-confidence architecture chat import proved (ADR-16). Zero-dep mbox/RFC 822/MIME parsing (`src/ingest/mbox.js`, per ADR-8's best-effort rules: encoded-words, base64/quoted-printable, multipart walking, charset fallback, attachments ignored) feeds pattern-based classifiers (`src/life/email-scan.js`) that emit `life_records` — receipt / subscription / renewal / booking — each with a `confidence` field, the evidence excerpt it was built from, and the Message-ID for idempotent re-import.

Three deliberate refusals shape the rail. **Not an archive:** bodies are read, matched, and discarded — only the ≤400-char evidence excerpt is stored; full-text mail is a different feature with different stakes. **Not a connector:** no IMAP/OAuth, ever — BYO-export is the trust architecture, not a v1 limitation. **Not a model pipeline:** heuristics only, so the rail runs on any machine with zero cost and zero cognition-sovereignty questions; model-assisted extraction can arrive later as an explicit opt-in behind the extractLocalOnly guarantees. The showcases (`src/life/insights.js`, `GET /api/life`, the Mind view's Life signals panel) are pure functions over the records — the subscription audit and renewals radar are the first cross-domain joins the WHY document promises, and their outputs are labeled as estimates from pattern matching, with known limits (US-style date reading, currency coverage) documented instead of smoothed over.

### ADR-22: Riding open weights — the serve rail, weight-digest receipts, and license disclosure
Open-weights releases are this product's demand engine: weights alone are an engine block, and every layer we own is the rest of the car. Three additions convert that tailwind into rails:

1. **The serve rail** (`sovereign byoc gpu serve <provider> --gpu-type id --model <hf-id>`): rents a container-style GPU (RunPod/Vast.ai) running vLLM's OpenAI-compatible server with the chosen open weights — for the class no local engine holds (300B+; ADR-25 brought the 20B–120B-total sparse MoE tier back onto owned hardware) — then hands back the endpoint and a once-shown API key (`--wire` writes it into the OpenAI-compatible provider slot only when that slot isn't already claimed). Same disclosed trust deviation as rail 1.5 (the key transits this CLI as instance env; hash stored), same unverified-against-live-infra warning, same one-command destroy that stops billing. VM-style providers get a documented manual recipe instead of a pretend rail. Readiness polls `/v1/models` with a generous timeout because weight download dominates first boot — the plan says "hundreds of GB" out loud.
2. **Weight-digest receipts**: assistant messages record `model_digest` — the exact Ollama weights that produced the reply (resolved in parallel with the stream, 60s cache, NULL for providers that expose no digest — unknown, not guessed). The chat meta line shows `weights <digest>`; the export format carries it. This extends "receipts on every memory" down into the model layer, matching the digest-gated rigor Fine-Tuning Studio already had.
3. **License at the point of use**: the Hugging Face browser now surfaces each repo's declared weight license in search results and the file list ("unlisted — check the repo" when absent, never guessed), and picking a GGUF auto-notes the declared license on the recipe's license field. Open weights are not open license; the UI says so where the choice happens.

### ADR-23: Small models are a product surface — the starter shelf and the cognition role
The SLM wave (Gemma, Qwen, Phi, SmolLM, Liquid's LFM, distilled R1) is almost entirely open-weight and is the class that actually fits our users' hardware — and it maps onto a distinction this product already makes: the model that *chats* can be anything, but the models that do the product's own cognition should be small, fast, and local. Two additions:

1. **The starter shelf** (`src/model-shelf.js`, `GET /api/model-shelf`, Model Studio panel): a curated list of small open-weight models organized by JOB (everyday chat, memory & cognition, reasoning, coding, embeddings, vision), each entry carrying its weight license, approximate Q4 footprint, a fit badge sized against this machine, and a stated reason for being there. Curation is versioned opinion, not a leaderboard: `curatedAt` is displayed, the note says the landscape churns, and entries without a reason or license fail the test suite. One click applies a pick to the role it belongs to — base model, embedding model, or cognition model.
2. **The cognition role** (`memory.extractionModel`): when set, every memory-writing call (auto-extraction, distillation) runs this model on the default provider, regardless of which model handled the chat. Combined with `extractLocalOnly`, this completes the cognition-sovereignty story from ADR-20: rent a frontier model for conversation while a 4B model you possess decides what is learned about you — and the author receipt on each memory names it.

### ADR-24: The core license is fair source (FSL-1.1-MIT)
The core is licensed FSL-1.1-MIT — self-hosting, forking, and internal use are unrestricted; only a competing commercial offering is barred, and each release irrevocably converts to plain MIT on its second anniversary, making the anti-lock-in covenant license text instead of goodwill. Plain permissive licensing was rejected because it lets a hosted competitor sell the finished product without funding it (a trademark forces a rename, but a renamed clone with a marketing budget is still a clone); AGPL because it doesn't restrict hosting unmodified code (no revenue defense); permanent non-competes (SSPL/Elastic) because a product that audits exits cannot have a "trust us" exit itself. Inbound contributions are MIT under the DCO (no CLA); the thin-client integrations remain MIT for store distribution. See [`docs/LICENSING.md`](LICENSING.md).

### ADR-25: FreeToken is a recognized engine, not a dependency — the frontier MoE tier comes home
[FreeToken](https://github.com/FlashML-org/FreeToken) (FlashML / Berkeley, Apache-2.0) is an edge-native MoE serving engine: expert weights live in host RAM, an LRU cache of experts sits on the GPU, and each step's misses stream over PCIe or compute on the CPU — so a 35B-total / 3B-active model runs on an 8 GB laptop GPU, and ~120B-total models on a gaming desktop with enough RAM. It speaks the OpenAI and Anthropic wire formats on loopback with no auth. That moves the practical ceiling of "local" from the SLM class (ADR-23) to the mid-size frontier class — the tailwind ADR-22 named — and it rewrites one of ADR-22's sentences: the rented-GPU serve rail is now for what *no* local engine holds, not for "the MoE class". Four decisions, and why the alternatives lost:

1. **A first-class `freetoken` provider id, not a preset in the OpenAI-compatible slot.** A preset would have been three lines, but the OpenAI slot is single-occupancy (the serve rail's `--wire` already claims it), the receipts would have read `author_provider: openai` for memories a FreeToken-served model wrote, and the starter shelf could not have verified "this entry needs FreeToken" without sniffing port numbers. `src/providers/freetoken.js` reuses the OpenAI-compatible stream parser and adds a real health check against FreeToken's `/health` lifecycle (`loading` with byte progress, `ok` + `maintenance: serving`, `error`) — a loading or rebuilding engine reports as unavailable, because chat would 503. Locality stays ADR-20's hostname rule: a FreeToken on the LAN is remote for "cognition stays home", exactly like a LAN Ollama. It is not a dependency: nothing imports it, the default is disabled, and `sovereign doctor` reports a running-but-unconfigured engine as an `[info]` line with a next step — never a failure. `FREETOKEN_BASE_URL` mirrors `OLLAMA_BASE_URL` for Docker and also enables the provider, since setting the URL is the intent.
2. **Reasoning is shown live and never stored.** FreeToken splits chain-of-thought into `reasoning_content` deltas (Ollama's `thinking` and Anthropic's `thinking_delta` are the same idea); the gateway now yields `{type:'reasoning'}`, chat forwards it as its own SSE event, and the browser renders it in a collapsible panel that says so: "shown live, not saved". Persisting it was rejected for now — it would widen the export format for text the model itself treats as scratch — and it is never appended to the answer, so memory extraction, `/api/ask`, and MCP see only what the model actually said. The `done` event carries `reasoningChars` so the token count on the meta line stays explainable.
3. **Sizing is two numbers now, not one.** The dense heuristic (0.6 GB per billion params at Q4 against 60% of RAM) is wrong for sparse models in both directions: the total weights must fit host RAM, but only the active set has to fit VRAM. The shelf gains a frontier MoE tier (`role: frontier-moe`, `engine: freetoken`, entries carrying `activeParamsB`) whose `fit` badge keeps the conservative total-weights RAM rule and adds a separate `gpuFit` for the active set when the GPU is known. An entry may override its group's engine: Nemotron 3.5 Lightning ships as GGUF and Ollama pulls it directly (`engine: 'ollama'`), so it is sized by the Ollama locality gate on the RAM rule alone — no `gpuFit`, because Ollama keeps the whole weight set resident rather than streaming an active set — and it stays out of the FreeToken recommendation's candidates until FreeToken's model list names it. That GPU comes from `src/hardware.js`, a best-effort zero-dep probe (`nvidia-smi`, then Linux sysfs; Apple Silicon reports unified memory and defers to the RAM rule; `SOVEREIGN_HARDWARE_PROBE=off` disables it). NVIDIA-only was accepted because FreeToken is NVIDIA-only; the Windows WMI/registry paths were rejected (uint32 `AdapterRAM`, `wmic` gone on 24H2). Unknown stays unknown: no readable GPU means no GPU badge, not a guess.
4. **What we still don't claim.** FreeToken is weeks old (v0.1.x), Linux-pip or Windows-desktop-app only, Ampere+/CUDA 13, and ships without request auth — the provider defaults to loopback and the docs say to keep it there. The model layer in the [ledger](SOVEREIGNTY.md) stays 🔴 Borrowed: the weights are still someone else's artifact; what changed is how much of the frontier now runs on hardware the user owns. The first-run wizard does not yet offer FreeToken (Settings → Providers does); that is the next rung, not a limitation to hide.

### ADR-26: The customs declaration — what leaves is shown before it leaves
ADR-20 and ADR-25 disclose *which* model answers and whether it runs on your hardware. They do not show *what it reads*: the system prompt, the memory notes selected for this turn, the retrieved document excerpts, the trimmed history, and the new message all cross the wire to a remote provider as one opaque request. "Remote · Anthropic" on a badge is a label; the bytes are the fact. Five decisions:

1. **The preview is the request.** Context assembly was split out of `handleChat` into a side-effect-free `assembleChatRequest` (persona → trimmed history → memory selection → retrieval → system prompt → the exact `messages` array), and both `POST /api/chat` and `POST /api/chat/preview` call it. The preview therefore shows byte-for-byte what the send will carry — it cannot drift, because there is no second code path. A preview writes nothing: no conversation, no message, no memory (retrieval runs; it is a read). The manifest carries the endpoint *host* only — never an API key, never a full base URL — and is tested for both.
2. **Local never gates.** `isLocalProviderEndpoint` (ADR-20's rule, now also reported as `local` on every `/api/providers` row) decides. A loopback or Docker-internal endpoint means nothing leaves, so nothing is asked and `outgoing` is `null`. `privacy.outgoingPreview` (`ask` | `off`, default `ask`) and `privacy.outgoingPreviewTrusted` (provider ids the user chose "don't ask again" for, validated as known ids, revocable as chips in Settings) only ever narrow the gate for remote sends.
3. **Every remote answer carries a receipt.** The SSE `meta` event gains `outgoing: { bytes, chars, approxTokens, host }` and the message line reads "left the machine · 6.2 KB → api.openai.com". "bytes" has one definition everywhere: the UTF-8 length of the JSON serialization of the outgoing context array — the system prompt as a leading system-role message when present, then the trimmed history, then the new user turn. That is exactly the `messages` array an OpenAI-compatible or Ollama endpoint receives; Anthropic carries the same content as `system` + `messages`. `approxTokens` is `ceil(chars / 4)` and says so — an estimate, not the provider's count (that arrives in `done.usage`).
4. **Headless surfaces do not gate, and are told so.** The CLI, `/api/ask`, MCP `ask_sovereign`, the editor and browser integrations, and ChatGPT Actions have no user in front of them to answer a dialog; a blocking prompt there would be a hang, not a disclosure. They send exactly as before, their docs say the declaration is a web-UI feature, and the receipt data is still on the wire for any client that wants to show it.
5. **No PII classifier, by design.** The obvious "smarter" version — scan the outgoing context for names, card numbers, addresses, and warn — was rejected: a classifier is another model reading your data, with its own false negatives that would turn a green light into a lie. The user sees the actual bytes, expandable part by part, rendered as text. What counts as sensitive is theirs to decide, and they can decide it every time or trust a provider once.

## Data model

`personas` (system prompt, provider/model override, memory/knowledge switches) · `conversations` (imported ones also carry `external_id`/`source_platform` for idempotent re-import, and `distilled_at` for idempotent memory sweeps) → `messages` (role, content, provider, model, token usage) · `memories` (long-term notes with provenance: `origin`, `source_conversation_id`, `updated_at`, `author_provider`/`author_model`) · `life_records` (heuristically extracted receipts/subscriptions/renewals/bookings with confidence, evidence excerpt, and source Message-ID) · `documents` → `chunks` (content + optional embedding JSON) · `model_recipes` (portable Ollama build specification and last-build metadata) · `training_projects` → `training_examples` → immutable `training_datasets` → `training_runs` (submission consent, state, metrics, artifact attestations, evaluation decision, deployment lineage).

Full export = all twelve data tables in one checksummed JSON archive ([format spec](EXPORT_FORMAT.md), optionally passphrase-encrypted). Configuration is omitted entirely: provider/trainer URLs, model defaults, bearer tokens, and API keys are reconfigured separately after restore. Imported training snapshots are treated as untrusted and revalidated before submission.

## Testing

Live artifact creation remains operator-dependent; deterministic tests use protocol-faithful mock trainer and Ollama endpoints.
